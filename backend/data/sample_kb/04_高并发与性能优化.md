# 智能订单交易系统 · 高并发与性能优化

## 1. 高并发挑战

大促场景下，系统面临的核心挑战：

- **瞬时流量洪峰**：零点开抢，QPS 从千级瞬间飙升至十万级。
- **热点商品**：爆款商品库存竞争激烈，单 key 成为瓶颈。
- **数据库压力**：若所有请求直达数据库，连接池与磁盘 IO 迅速打满。
- **级联故障**：一个下游服务变慢，拖垮整个调用链。

应对思路：**缓存挡、异步削、限流防、降级保**。

## 2. 多级缓存

读多写少的数据（商品详情、库存、配置）采用多级缓存：

1. **本地缓存（Caffeine）**：应用进程内缓存，纳秒级访问，缓存热点配置类数据，TTL 60 秒。
2. **分布式缓存（Redis）**：跨实例共享，缓存商品详情、用户信息，TTL 5 分钟。
3. **数据库**：缓存未命中时回源查询，并通过"缓存空值"防穿透。

**缓存一致性**：数据更新时先删缓存再更新数据库，配合延时双删策略避免脏读。库存等强一致数据不走本地缓存，仅用 Redis。

## 3. 异步化与削峰

将非核心链路异步化，降低主链路响应时间：

- **下单后置操作异步**：下单成功后，积分发放、消息推送、日志记录等通过 MQ 异步执行，不阻塞下单主流程。
- **流量削峰**：秒杀场景下，前端请求先进入 MQ 队列，后端按消费能力匀速处理，避免直接冲垮数据库。
- **批量写优化**：库存扣减流水先写内存，定时批量刷库，降低数据库写入压力。

## 4. 限流与熔断

通过 Sentinel 实现多维度限流：

- **接口级限流**：下单接口设置 QPS 阈值，超出返回"系统繁忙"。
- **用户级限流**：防刷，单用户每秒下单次数限制。
- **集群限流**：基于 Redis 计数，限制全集群总 QPS。

**熔断策略**：当下游服务（如支付渠道）错误率超过 50% 时触发熔断，直接走降级逻辑，避免拖垮自身。

## 5. 数据库优化

- **分库分表**：订单表按用户 ID 取模分 64 库 64 表，单表数据控制在 1000 万以内。
- **读写分离**：查询走从库，写操作走主库，通过 ShardingSphere 路由。
- **索引优化**：高频查询字段建立联合索引，避免全表扫描。
- **SQL 审查**：慢查询监控，P99 超过 100ms 的 SQL 必须优化。

## 6. 热点库存优化

爆款商品库存是典型的热点 key，单 Redis 节点会成为瓶颈。采用"库存预热分桶"方案：

1. 将 1000 件库存拆分到 10 个 key（stock_1 ~ stock_10），每个 key 承载 100 件。
2. 下单时随机选一个分桶扣减，失败则换桶重试。
3. 这样把单 key 的写入压力分散到 10 个 key，避免热点。

## 7. JVM 与容器优化

- **JVM 调优**：使用 G1 收集器，设置 `-XX:MaxGCPauseMillis=100` 控制停顿时间。
- **容器化部署**：每个微服务打包 Docker 镜像，通过 K8s 调度，大促前自动 HPA 扩容。
- **资源隔离**：核心交易服务与非核心服务（如报表）部署在不同节点池，避免资源争抢。

## 8. 全链路压测

上线前必须经过全链路压测：

1. 生产环境录制真实流量，在压测环境回放。
2. 逐步加压，找出系统瓶颈点（数据库、缓存、网络）。
3. 根据压测结果调整容量水位与扩容阈值。

## 9. 监控体系

- **指标监控**：Prometheus + Grafana，监控 QPS、延迟、错误率、JVM 内存。
- **链路追踪**：SkyWalking 追踪请求全链路，定位慢调用。
- **日志**：ELK 收集日志，支持按订单号串联查询全链路日志。
- **告警**：核心指标超阈值通过钉钉/电话实时告警，做到 5 分钟内响应。

## 小结

高并发优化的核心是"分层防御"：缓存挡住读、异步削掉写、限流防住洪峰、降级保住核心。没有银弹，需根据实际压测数据持续调优。至此，智能订单交易系统的架构、业务、事务、性能四大主题讲解完毕。
