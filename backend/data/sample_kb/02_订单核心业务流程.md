# 智能订单交易系统 · 订单核心业务流程

## 1. 订单全生命周期

一笔订单从创建到完结，经历以下核心状态：

```
待支付 → 已支付 → 待发货 → 已发货 → 已签收 → 已完成
   ↓        ↓        ↓
 已取消   已退款   已取消
```

订单状态机是交易系统的"中枢神经"，每一次状态跳转都必须有明确的触发事件和前置校验，禁止出现非法状态迁移。

## 2. 下单流程详解

用户点击"提交订单"后，系统串行执行以下步骤：

1. **参数校验**：校验商品 SKU、收货地址、购买数量是否合法。
2. **风控预检**：调用风控服务，判断是否触发限购、是否命中黑名单。
3. **营销计算**：营销服务根据用户持有的优惠券、会员等级，计算最终优惠金额。
4. **库存预扣**：库存服务对下单商品执行预扣减（pre-deduct），防止超卖。
5. **订单落库**：将订单主表、订单明细写入 MySQL，状态为"待支付"。
6. **发送延时消息**：向 RocketMQ 发送一条 30 分钟延时消息，到期未支付则自动取消订单并回滚库存。
7. **返回结果**：向用户返回订单号，引导跳转支付。

## 3. 库存扣减策略

库存是电商交易的核心数据，扣减策略直接影响超卖与性能。系统采用"预扣 + 确认"两阶段方案：

- **预扣阶段（下单时）**：在 Redis 中扣减库存缓存，并在 MySQL 记录一条"预占"流水，设置 30 分钟过期。
- **确认阶段（支付成功后）**：将预占转为真实扣减，更新商品可售库存。
- **回滚阶段（超时未支付/取消）**：释放预占，恢复 Redis 与 MySQL 库存。

为防止并发超卖，预扣阶段使用 Redis Lua 脚本保证"查询 + 扣减"原子性，并在 MySQL 层通过 `UPDATE ... WHERE stock >= qty` 行锁兜底。

## 4. 支付与回调

支付服务对接多渠道，流程如下：

1. 订单服务调用支付服务创建支付单，支付服务向第三方渠道发起预下单。
2. 第三方返回支付参数（如微信预支付 ID），前端拉起收银台。
3. 用户完成支付后，第三方异步回调支付服务。
4. 支付服务**验签**后，更新支付单状态，并通过 RocketMQ 发送"支付成功"消息。
5. 订单服务消费该消息，将订单状态由"待支付"流转为"已支付"，触发库存确认与发货通知。

**关键点**：第三方回调可能重复发送，支付服务必须做**幂等处理**，通过支付单号唯一约束保证一笔订单只会被成功处理一次。

## 5. 取消与退款

订单取消分主动与被动两种：

- **主动取消**：用户在待支付状态主动取消，直接回滚库存。
- **超时取消**：延时消息触发，系统自动取消未支付订单并回滚库存。
- **退款**：已支付订单发起退款，需走审批流，审批通过后调用第三方退款接口，退款成功后订单状态变为"已退款"。

## 6. 订单幂等设计

下单接口必须保证幂等，防止用户快速双击造成重复下单。方案：客户端生成唯一 `requestId`，服务端在 Redis 中记录该 requestId（设置 5 分钟过期），若已存在则直接返回首次下单结果。

## 小结

订单流程是交易系统的核心脉络。状态机严谨、库存两阶段扣减、支付幂等、下单幂等，这四点是保障交易正确性的基石。下一章将讨论分布式事务如何保证跨服务数据一致性。
